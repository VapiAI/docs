Design the conversation around the caller's current intent and the status of the task. The speaker can keep talking while work proceeds, so an acknowledgment must stay distinct from a confirmed result.

## Track conversation and action separately

Three events can happen at different times: the caller finishes speaking, the tool returns, and the caller hears the result. Treat each as evidence of its own outcome.

| What happens | What it establishes | What it does not establish |
| --- | --- | --- |
| Caller interrupts | New speech needs attention | A pending operation was cancelled |
| Assistant says “I'll check” | It acknowledged the request | A lookup started or succeeded |
| Tool reports available slots | The lookup returned availability | A slot is reserved |
| Booking service confirms an operation | The booking succeeded | The caller heard the confirmation |
| Connection closes | The conversation ended | External work was rolled back |

## Handle a correction during a lookup

Consider this exchange:

> **Caller:** What do you have on Thursday?  
> **Assistant:** I'll check.  
> **Caller:** Actually, Friday afternoon.

The corrected task is Friday afternoon. The speaker should acknowledge that change without reading out Thursday's results as the answer.

Your service should associate requests with the current task. For example, keep a task revision with the requested date and time zone. Before using a returned result or executing a booking, verify that it still matches the current request. This is an application design pattern, not a Vapi configuration field.

If the Thursday lookup cannot be cancelled, let it finish and mark its result as outdated. If an action already changed a record, report that state and use your service's change or cancellation procedure.

## Ask for the missing decision

Ask one short question that makes the next action possible. An appointment request may need a date, time zone, appointment type, or confirmation of a specific slot.

Prefer “Which time zone should I use?” to asking the caller to repeat the entire request. When a correction invalidates a previous confirmation, obtain a new confirmation for the revised action.

Short acknowledgments can keep a conversation understandable. Avoid instructions that require a filler phrase before every tool call; evaluate whether the assistant's timing is useful in real audio.

## Explain work in progress accurately

Use language that matches what the service knows:

| Task status | Example spoken response |
| --- | --- |
| Lookup pending | “I'm checking Friday afternoon.” |
| Slots returned | “There are openings at two and four. Which works for you?” |
| Booking pending | “I'm submitting the two o'clock appointment.” |
| Booking confirmed | “Your two o'clock appointment is booked.” |
| Outcome unknown | “I haven't confirmed whether that booking went through yet.” |
| Cancellation confirmed | “The appointment has been cancelled.” |

The examples illustrate meaning, not guaranteed verbatim speech. Choose one useful update when work is slow instead of repeatedly announcing the same pending state.

## Treat cancellation as an operation

“Stop talking,” “stop checking,” and “cancel my appointment” have different effects. Ask a brief clarification when the intended action is unclear.

Put cancellation and duplicate prevention in the service that owns the action. A timeout or lost response can leave an operation's outcome unknown. Reconcile that outcome before retrying a write. Use an operation identifier so a retry cannot silently create a second booking.

## Choose where exact wording matters

GPT-Live generates speech and can paraphrase supplied text. Test language, pronunciation, and required phrases with audio; a matching text prompt does not establish verbatim delivery.

If your application requires an exact prerecorded opening or approval before any audio plays, check the [compatibility reference](/gpt-live/configuration) before choosing this integration. Do not assume that withholding a reasoner result pauses the speaker.

## Evaluate the whole exchange

Test corrections during speech, during a lookup, and immediately before a write. For each test, inspect the audio, tool results, and final record in your service.

OpenAI's [migration guide](https://developers.openai.com/api/docs/guides/live-migration) discusses the separation between interruption and backend cancellation. The [Vapi testing guide](/gpt-live/testing) turns these cases into a repeatable comparison.
