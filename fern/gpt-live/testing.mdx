Validate the migrated assistant against representative calls and final service records. A fluent conversation is only one part of success; the assistant must also perform the correct actions and end the call cleanly.

## Prepare a migration

<Steps>
<Step title="Record the current behavior">
Collect representative call scenarios, expected actions, and final records. Include errors and corrections, not only successful requests. Use test data with a repeatable starting state.
</Step>
<Step title="Check compatibility">
Compare the assistant's transports, tools, greetings, and fallback plans with the [compatibility reference](/gpt-live/configuration). Resolve dependencies on unsupported features before replacing the assistant.
</Step>
<Step title="Split the prompt">
Move conversational guidance into the speaker prompt and detailed procedures into the reasoner prompt. Retain validation and authorization in your services. See [Configure the speaker and reasoner](/gpt-live/prompts).
</Step>
<Step title="Create a separate test assistant">
Use `gpt-live-1` and a supported OpenAI voice. Connect test tools, then confirm a basic call and an end-call request before testing business actions.
</Step>
<Step title="Run the same scenarios">
Repeat each scenario against both assistants. Record intentional differences and regressions. Do not route production calls to the new assistant until its required behaviors pass.
</Step>
</Steps>

## Test conversation and task outcomes

Use this matrix as a starting point for an appointment assistant:

| Scenario | Check in the audio | Check in your service |
| --- | --- | --- |
| Ask for availability | Speaks the returned slots | Correct date and time zone queried |
| Change Thursday to Friday during lookup | Uses the corrected request | Outdated lookup cannot drive a booking |
| Interrupt an answer | Responds to the new request | No accidental duplicate action |
| Confirm one offered slot | Announces success only after confirmation | Exactly one booking for that slot |
| Tool responds slowly | Gives accurate pending information | Operation remains traceable |
| Tool fails | Explains failure without inventing a result | No successful write recorded |
| Response is lost after a write | Treats the outcome as uncertain | Status reconciled before retry |
| Ask to cancel | Distinguishes request from completion | Cancellation status verified |
| Disconnect during work | New call does not assume completion | Pending work reconciled |
| Ask to end the call | Conversation ends | Call record reaches an ended state |

Include the languages, background noise, names, and speaking styles your callers use. Voice previews demonstrate a voice; they do not replace application testing.

## Measure useful outcomes

Track task completion, incorrect actions, duplicate writes, and the time to a useful spoken answer. Record first-audio timing separately so a quick acknowledgment does not hide slow or unsuccessful work.

Use the same starting state and success criteria when comparing configurations. Repeat trials because generated conversations vary. Increase reasoning effort only when the improvement in task outcomes justifies its effect on response time and cost.

OpenAI's [voice evaluation guide](https://developers.openai.com/cookbook/examples/audio/voice_agent_evaluation) provides additional evaluation methods. Adapt them to the outcomes your Vapi assistant must achieve.

## Use Simulations and Evals appropriately

Vapi [Simulations](/observability/simulations-overview) provide scenarios, AI tester personalities, and success criteria for repeatable conversations. Use the scenario matrix above to define what a GPT-Live test should cover.

The current voice simulation bridge uses 16 kHz audio and listen sockets. GPT-Live's raw WebSocket connection requires 24 kHz audio and does not provide those listen sockets, so the current voice simulation path is not compatible. Use calls through a supported GPT-Live transport to exercise these scenarios until a compatible simulation path is available.

[Evals](/observability/evals-quickstart) test supported model decisions using configured inputs and expected behavior. They do not establish full-duplex timing, interruption handling, or audio quality. A passing text evaluation or chat simulation is not evidence that a GPT-Live voice call works.

## Analyze outcomes after calls

Configure [structured outputs](/assistants/structured-outputs) to extract consistent fields from completed calls. For the appointment example, useful fields include the requested date, whether the caller corrected it, and whether the assistant announced a confirmed booking.

Use [scorecards](/observability/scorecard-quickstart) to grade those outputs against your criteria. Keep conversational evidence separate from service evidence: a transcript-based grade cannot establish that exactly one appointment exists in your database.

Existing `analysisPlan` configurations also use the shared post-call analysis path. For new extraction and evaluation setups, follow the [call analysis guide's recommendation](/assistants/call-analysis) to use structured outputs.

## Monitor production quality

Use [Boards](/observability/boards-quickstart) to inspect outcome trends and [Monitoring](/observability/monitoring-quickstart) to alert on configured thresholds. Start with failed calls, failed task outcomes, and changes in the rate of unresolved requests.

Choose an evaluation window and threshold that match your traffic. Review the affected calls when an alert fires, then turn confirmed failures into repeatable test scenarios. Sample unflagged calls too; a monitor only detects the conditions you configure.

Monitoring requires retained call data and is unavailable with Zero Data Retention. It evaluates call quality and outcomes; it does not provide a live listen connection to the GPT-Live session.

## Inspect call evidence

Use the [Vapi call record and artifacts](/assistants/retrieve-call-artifacts) to inspect the ended reason, messages, tool activity, and available artifacts. Compare returned tool results with your service's logs and operation identifiers.

Check recording settings before relying on audio artifacts. Recording is disabled when a recording-consent plan is configured for this integration. Preserve suitable test evidence through an approved recording setup.

Transcripts are useful for reviewing words. Listen to audio when judging timing, interruption handling, pronunciation, or what the caller actually heard.

## Troubleshoot common failures

Start with the symptom, then verify its likely cause:

| Symptom | Check | Fix |
| --- | --- | --- |
| GPT-Live is unavailable | Organization feature access | Contact Vapi to enable access. |
| Voice rejected | `voice.provider` and `voice.voiceId` | Use OpenAI and a [supported voice ID](/gpt-live/voices). |
| Assistant save rejects tools | Tool type and resolved names | Use supported types and unique names; inspect saved tools too. |
| Call fails on WebSocket startup | Audio format and sample rate | Set raw `pcm_s16le` at `24000` Hz explicitly. |
| WebSocket audio sounds distorted | Sample encoding, rate, and channels | Convert the source to mono, signed 16-bit little-endian PCM at 24 kHz. |
| Assistant never greets | First-message mode and usable text | Set `assistant-speaks-first` and a text `firstMessage`. |
| Assistant promises a lookup but no tool runs | Both prompts and attached tools | Add a concrete delegation rule and make the tool available to the reasoner. |
| Tool result never reaches the conversation | Handler response and matching ID | Return the actual `toolCallId`; complete asynchronous work through its supported contract. |
| Transfer fails | Transport and configured destination | Use a supported blind transfer; check carrier requirements and destination restrictions. |
| No recording | Recording settings and consent plan | Check the documented recording behavior before the test. |

## Finish or roll back a test

End active calls using the call interface or `endCall`. Disconnect test WebSocket clients and verify that the calls ended. Review any external operations still pending after disconnect.

Keep the previous assistant available during migration. To roll back, route new calls to that assistant. Reconcile actions already submitted by the test assistant; changing call routing does not undo those actions.

For more background on preserving application state and procedures, see OpenAI's [migration guide](https://developers.openai.com/api/docs/guides/live-migration).
