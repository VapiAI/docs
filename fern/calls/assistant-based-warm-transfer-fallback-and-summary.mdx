This guide covers three `warm-transfer-experimental` behaviors that are easy to misconfigure once you have a transfer assistant running: what the caller hears when the transfer fails, how to point the operator summary at your own model, and how to stop the transfer assistant from completing a transfer into an IVR or hold queue. Start with [Assistant-based warm transfer](/calls/assistant-based-warm-transfer) to configure the base tool before using this guide.

## Expected behavior when a transfer fails

When the transfer assistant cannot reach the destination (unanswered, busy, or the operator declines), Vapi should:

1. Speak `fallbackPlan.message` to the caller.
2. End the call according to `fallbackPlan.endCallEnabled` — either end the call after the message, or return the caller to the original assistant.

<Callout intent="warning">
Known issue: some `warm-transfer-experimental` configurations do not speak `fallbackPlan.message` on a failed transfer. Instead, the caller hears the `summaryPlan` briefing text, and the call ends with `endedReason: call.in-progress.error-transfer-failed`. Disabling `summaryPlan` removes the wrong message, but the call can then end with `endedReason: assistant-forwarded-call`, which misreports a failed transfer as successful.
</Callout>

If you hit this, it is not a configuration mistake on your side — treat both symptoms above as reportable bugs. Before contacting support, capture:

- The `id` of the affected call.
- Whether `summaryPlan` was enabled or disabled at the time.
- Both the spoken message the caller actually heard and the `endedReason` from the call log.

This lets support distinguish the two known failure modes above from a genuinely new one.

## Custom summary model with `summaryPlan.customLlmUrl`

`summaryPlan.customLlmUrl` is intended to let your own model generate the operator-facing summary for `warm-transfer-experimental`, instead of Vapi's internal model. Configure it alongside the rest of `summaryPlan`:

```json
{
  "transferPlan": {
    "mode": "warm-transfer-experimental",
    "summaryPlan": {
      "enabled": true,
      "customLlmUrl": "https://your-server.example.com/v1/chat/completions",
      "messages": [
        { "role": "system", "content": "Summarize this call for the operator in two sentences." },
        { "role": "user", "content": "{{transcript}}" }
      ]
    }
  }
}
```

<Callout intent="warning">
Known issue: multiple customers have configured `customLlmUrl` and confirmed (via their own server logs) that Vapi never sends a request to it — the summary is generated by Vapi's internal model instead. If your server does not receive a request when a transfer completes, this is currently expected; `customLlmUrl` support for `warm-transfer-experimental` is not yet confirmed working end-to-end.
</Callout>

Until this is confirmed fixed, verify your setup before assuming your endpoint is broken:

- Confirm `summaryPlan.enabled` is `true` and `customLlmUrl` is on the same `summaryPlan` object as your `messages`.
- Confirm your endpoint accepts an OpenAI-compatible chat-completion request and returns a 2xx response within `summaryPlan.timeoutSeconds`.
- If your server still receives nothing, report it to support with your tool ID and a call ID where the summary ran — this is the same signal engineering needs to confirm the bug.

## Preventing a transfer into an IVR or hold queue

The transfer assistant decides the transfer outcome by calling `transferSuccessful` or `transferCancel`. If the destination answers with an automated hold message (for example, "please hold for the next available representative") instead of a live operator, the transfer assistant can mistake that for a successful handoff and call `transferSuccessful` — dropping the caller into a queue with no one aware a transfer happened. Vapi reports this outcome as `endedReason: call.forwarding.operator-busy` on the destination leg.

To prevent this, tell the transfer assistant explicitly what a non-human destination sounds like. Add prompt language such as:

> "If the destination plays a hold message, an automated queue announcement, or any message that does not sound like a live person addressing you directly, call `transferCancel`. Only call `transferSuccessful` after a live person responds to you."

If you want the caller connected into that queue rather than returned to the original assistant, that is a separate telephony-level configuration on the destination call leg, not something the transfer assistant's success/cancel decision controls — treat an unexpected `call.forwarding.operator-busy` as a signal to check your destination's IVR/queue behavior, not just your prompt.
