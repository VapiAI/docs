title: "Debug call forwarding drops"
subtitle: "Trace transfer attempts, failed connections, and caller recovery"
description: Diagnose transfer tool invocation, provider routing, busy and unanswered destinations, fallback behavior, and the evidence to send Support.
---

An assistant saying it will transfer, Vapi starting a transfer, and the destination answering are separate events. Use the call record and provider logs to find where the attempt stopped.

## Quick diagnosis

| What you observe | Check next | Likely owner |
| --- | --- | --- |
| The assistant says it will transfer, but the call continues | Look for a `transferCall` invocation in the call's **Messages** tab | Assistant prompt or model decision |
| The `transferCall` tool runs, but the transfer does not start | Inspect the call's **Logs** tab for a Tool or Transfer error | Tool configuration or Vapi transfer initiation |
| The call ends with `assistant-forwarded-call`, but the destination does not answer | Match `phoneCallProviderId` to the provider's call record | Provider route, destination, or delegated call control |
| A warm transfer returns to the original assistant or ends after a fallback message | Check `transferPlan.mode`, `fallbackPlan.endCallEnabled`, and the transfer attempt | Configured fallback or transfer-assistant decision |

`assistant-forwarded-call` means Vapi started or handed off the transfer. It does not prove that the destination rang, answered, or spoke with the caller.

## Prerequisites

Before you start debugging, ensure you have:

- **Call ID** from the dropped call
- **API access** to make GET requests to Vapi
- **Access** to the call's **Messages** and **Logs** tabs, when logs were retained
- **Access** to the phone provider's call record, if the transfer reached that provider
- **A SIP trace or packet capture** when debugging a SIP transfer and one is available

## Troubleshooting workflow

<Steps>
<Step title="Check call ended reason">

First, check the call's `endedReason` and the [Messages tab](/observability/logs/call-logs#messages). A spoken promise to transfer is not a `transferCall` invocation.

<CodeBlocks>
```bash title="cURL"
curl -X GET "https://api.vapi.ai/call/{call_id}" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json"
```

```typescript title="TypeScript SDK"
import { VapiClient } from "@vapi-ai/server-sdk";

const client = new VapiClient({ token: process.env.VAPI_API_KEY });
const call = await client.calls.get("YOUR_CALL_ID");
console.log("End reason:", call.endedReason);
```

```python title="Python SDK"
import os
from vapi import Vapi

client = Vapi(token=os.getenv("VAPI_API_KEY"))
call = client.calls.get("YOUR_CALL_ID")
print(f"End reason: {call.ended_reason}")
```

</CodeBlocks>

**Interpret the result:**

- No `transferCall` tool call: check the assistant prompt and tool assignment. The model did not invoke the transfer tool.
- A `transferCall` tool call followed by a Tool or Transfer error: inspect the destination, transfer plan, and [call logs](/observability/logs/call-logs#logs).
- `assistant-forwarded-call`: Vapi submitted the transfer to the phone provider or sent a `phone-call-control` request to your server. Check the downstream result before treating it as a connected call.
- `call.in-progress.error-transfer-failed`, `call.forwarding.operator-busy`, or `call.forwarding.no-answer`: inspect the transfer attempt and provider result. These reasons do not all mean the assistant failed to invoke the tool.

</Step>

<Step title="Identify who controls the transfer">

When `phoneCallProviderBypassEnabled` is `true`, or the assistant includes `phone-call-control` in `serverMessages`, Vapi sends a `phone-call-control` request to your server instead of directly transferring the provider call. Check your server's response and provider-side action before changing either setting.

Use [Webhook logs](/observability/logs/webhook-logs) to inspect a recorded server-message delivery. If your application intentionally controls the provider call, its logs and provider call record are the source of the downstream outcome.

</Step>

<Step title="Validate transfer scenario compatibility">

The built-in phone and SIP transfer path requires a supported phone transport. A web call's WebSocket transport rejects both phone-number and SIP transfer destinations. A phone call can transfer to a phone number or SIP URI when its provider supports the configured route.

For a SIP destination, check the inbound provider, `transferPlan.sipVerb`, and the receiving private branch exchange (PBX). For a phone-number destination, verify E.164 format and call the number directly to confirm it is reachable.

</Step>

<Step title="Analyze telephony provider logs">

Use the call's `phoneCallProviderId` and timestamp to find the matching record in your phone provider's logs. Check whether the provider received the transfer command, dialed the destination, and recorded an answer, busy signal, no answer, rejection, or other failure.

A successful API command to the provider is not proof that the downstream call connected. Compare the provider record with the Vapi call's `endedReason`, [Messages](/observability/logs/call-logs#messages), and [Logs](/observability/logs/call-logs#logs). A missing provider record may indicate a Vapi initiation or configuration problem; a provider error identifies a downstream failure to investigate with that provider.

</Step>

<Step title="Analyze SIP packets (SIP calls only)">

For SIP trunking or bring-your-own-number setups, analyze the SIP signaling.

**Check whether a packet capture is available:**

```bash title="Get the call record"
curl -X GET "https://api.vapi.ai/call/{call_id}" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

For an eligible Vapi or bring-your-own SIP phone call, the completed call can contain `artifact.pcapUrl` when packet capture was enabled and retained. If present, download that URL and open the capture in a SIP analysis tool. A missing URL does not prove that no transfer command was sent.

**Filter for transfer packets:**

```text title="Wireshark filter"
sip.Method == "REFER"
```

**What to look for:**

- **REFER request present:** The transfer request reached the SIP signaling path captured in this file.
- **REFER response present:** Check the response code and any later NOTIFY or referred-call status. Acceptance of a REFER request alone does not prove that the destination answered.
- **No REFER request:** Check whether the transfer used `sipVerb: "dial"` or `sipVerb: "bye"`, whether capture started before the transfer, and whether the tool was invoked. Vapi phone numbers always dial the destination, so look for the dial leg instead.

With `sipVerb: "dial"`, inspect the outbound dial leg instead of looking for a REFER. With `sipVerb: "bye"`, Vapi ends its leg without dialing the destination.

For more details on SIP configuration, see our [SIP trunk documentation](https://docs.vapi.ai/advanced/sip/sip-trunk#inbound-call-test).

</Step>
</Steps>

## Diagnose busy, no answer, rejection, voicemail, and timeout

Recovery depends on the transfer mode. Check `transferPlan.mode` before changing a fallback setting.

| Mode or path | What to check | Caller recovery |
| --- | --- | --- |
| Blind transfer or non-assistant warm transfer | Provider call record for busy, no answer, rejection, voicemail, or a failed destination leg | On Twilio, Vapi hands the call to Twilio and ends with `assistant-forwarded-call`, even if the destination is busy or doesn't answer. The caller's call ends, and voicemail counts as answered. On Vapi numbers and SIP trunks, busy and no-answer can have their own ended reasons when outcome detection is enabled. Otherwise the call ends with `assistant-forwarded-call`. |
| `warm-transfer-experimental` | Operator-leg status, `transferAssistant` configuration, transfer-assistant tool call, and timeout | With `transferAssistant` configured, busy and no-answer statuses roll back. `transferCancel` can roll back a declined call or detected voicemail. The configured fallback message plays after rollback. |
| SIP cold transfer with organization-enabled fallback | Transfer outcome, `fallbackPlan`, and provider record | Recovery is conditional on organization enablement and the failure path. Confirm it with a controlled call before using it for a critical escalation. |

For assistant-based warm transfer, set `fallbackPlan.endCallEnabled` explicitly. `false` keeps the original assistant on the call after the fallback message; `true` ends the call after the message. Voicemail or an automated queue requires the transfer assistant to cancel, or configured voicemail detection to identify a non-human destination. Do not assume that a standard message, summary, or TwiML introduction detects voicemail.

A failed transfer command can end with `call.in-progress.error-transfer-failed`. On an organization-enabled SIP cold transfer, a configured `fallbackPlan` can also handle a recoverable transfer-request failure while the caller is still connected to Vapi. It cannot recover a call that has already ended. An operator-leg busy or no-answer outcome can produce a different reason or return the caller to the original assistant, depending on the mode and recovery configuration. Read the call's messages and logs with the ended reason rather than using that field alone to decide where the failure occurred.

## When to contact support

Contact Support when the tool was invoked with a supported configuration but the Vapi and provider records disagree, a transfer error has no clear cause, or the same failure persists across controlled calls.

**Include in your support request:**

- Vapi call ID, timestamp, call type, and `endedReason`
- Transfer tool ID, mode, destination type, and a redacted destination
- Expected caller and operator outcome, plus what each party heard
- Relevant **Messages** and **Logs** entries, including the transfer tool call and fallback behavior
- `phoneCallProviderId`, provider call record, error code, and SIP trace or `artifact.pcapUrl` when available
- Whether `phoneCallProviderBypassEnabled` or `phone-call-control` delegates call control to your server

## Next steps

Test the chosen transfer mode with a reachable operator, a busy destination, and an unanswered call before using it for production escalation. For SIP routing, compare the result with your [SIP trunk configuration](/advanced/sip/sip-trunk).
